# 成长后的 Agent：同一批真实项目重测 PK

> 心经体系沉淀后，用同一批真实项目、同任务提示词重测——对比裸模型与早期元规则的历史数据，量化"思考的组织方式"带来的增量

---

## 摘要

在已有"三模型全面数据 PK"（裸能力/元规则增量基线）的基础上，本篇文章回答一个新问题：**当同一个 Agent 经历了方法论沉淀（认知基石：毛线团/四维度/注意力/秘籍留白/领悟即固化）之后，重跑同一批真实业务任务，数据会怎么变？**

测试用**现在的体系**（心经体系 SYSTEMV1 全量版）重测四个真实业务场景：三个真实项目代码审查 + 一个性能优化，任务提示词与历史测试**一字不改**，与裸模型（Flash/Pro）和早期元规则（思维链）的历史数据同条件对比。

核心读数：

1. **审查总量 74 个问题**（项目A 16 / 项目B 16 / 项目C 42）——历史最好合计 72，总量追平并小幅超越；**但结构发生了质变**：项目C 从 30 → 42（+40%），且首次出现 S 级灾难分级（4 个）、实测验证的攻击链、以及"契约级"性能瓶颈发现。
2. **性能优化 8 个瓶颈**（全部带文件+行号+修复方案+验证方式）——追平历史最佳（8 个），但独有发现了"假后台"（函数名 batch、注释声称后台、实现却是阻塞等待）这类**契约与实现背离**的问题。
3. **诚实呈现**：项目A 16 个与裸 Flash 持平、项目B 16 个低于裸 Pro 的 30——数量上互有胜负；但深度上出现了历史没有的东西（见下）。

一句话：**数量竞争已不是重点，重点是同一个 Agent 的"发现结构"变了**——从"零散敏感点"变成"攻击链验证、灾难分级、契约审查"。

## PK 2：真实性能优化（项目C：3000+ 节点目录卡顿 + 上传整机卡）

### 瓶颈发现数量

| 体系 | 瓶颈数 | 是否带文件+行号 | 修复方案 | 验证方式 |
|------|:------:|:--------------:|---------|---------|
| 裸 Flash（历史） | 7 | 部分 | 7 修复 | 有 |
| 早期元规则·思维链（历史） | 7 | 部分 | 分层方案 | 有 |
| 早期元规则·用户版B（历史最佳） | 8 | 有 | 4 层方案 | 压测验证 |
| **心经体系（本次）** | **8** | **全部带文件+行号** | **5 方案按性价比排序** | **5 项含通过标准** |

### 本次独有发现（契约级）

1. **B3"假后台"**：`generate_thumbnails_batch` 函数名是 batch、注释写着"后台生成"，实现却是**每个文件 spawn 一个线程 + 主线程 Condvar 阻塞等待全部完成**——而前端根本不依赖它的返回值（已有 `thumbnail-ready` 事件逐张通知）。一个看似后台的接口，正是卡顿的元凶；好在代码里已存在非阻塞版本，修复方向是"复用已有正确机制"。
2. **B7 重复提交**：每次刷新清空缩略图"已提交"集合，与正在运行的生成任务重复（SQL 查重拦不住"生成中未写库"的）。
3. **根源 vs 出口**：`app.js:666` 的注释证明开发者早已知道全量刷新会卡死 UI，但只修了 `thumbnails-generated` 一个出口，`vault-changed` 这个更大的触发源反而漏了——"修了症状的一个出口，没修根源"。

**解读**：瓶颈数量追平历史最佳（8 个），但本次所有瓶颈都带文件+行号（可复现），方案按性价比排序（防抖合并→增量更新→并发化→去阻塞→虚拟滚动），验证方式含通过标准（如"50 次刷新→≤2 次"）——**从"发现问题"走向"可执行的工程方案"**。

## PK 3：同批逻辑/思维题的交叉验证

历史结论：裸模型 20/20 全对（基础逻辑无区分度）。本次重测 009（不确定性诚实）——**承认无法确定 + 列出缺失因素（路况/天气/交通方式/按时出门/工作日）+ 概率性判断但明确不确定性**，且表达方式内化了体系沉淀的类比（"昨天的 8:45 是一张昨天的照片，不是今天的天气预报"、"查房看到病历上写着昨天体温正常，今天该量体温还是得量"）。

**结论**：结果对错无区分（历史已证），**但表达结构有区分**——同一个诚实结论，带体系时会长出类比与画面，这是"可读性/可传播性"维度的增量。

## 核心结论

1. **数量竞争已结束，结构竞争刚开始**：审查总量 74 vs 历史最佳 72（+2），但项目C 单项目 30 → 42（+40%）且首次出现 S/H/M/L 四级分级——**同一个 Agent 的"发现结构"变了**：从零散敏感点 → 攻击链验证、灾难分级、契约审查。
2. **"实测验证"成为默认动作**：本次 3 处攻击链验证（Node 实测路径穿越、依赖源码逐行验证、DB 实查）——历史只有思维链偶发 2 处。**"验证意识"从偶发变成稳定行为**。
3. **契约审查是新维度**：假后台（batch 注释 vs 阻塞实现）、虚假加密（前端承诺 vs 恒等函数）、登录空壳（前端页面 vs 后端不存在）——这类"承诺与实现背离"的问题，裸模型和早期元规则都没有系统性发现。**查房四步里的"对契约"，在性能/安全之外找到了新的用武之地**。
4. **诚实呈现是数据可信的前提**：项目A 16 与裸 Flash 持平、项目B 16 低于裸 Pro 30——数量互有胜负，但项目B 的 16 个里含 1 个实测验证的任意文件删除攻击链 + 零鉴权 + 虚假加密（高危集中），项目A 的 16 个里含 SSRF + 删除复活 + MITM 注入链（安全密度高）。**数量少不等于质量低，单看总数会误判**。
5. **思考的组织方式 = 能力的乘数**：同一个模型、同一批代码、同任务提示词，仅仅因为体系不同，产出从"59-72 个问题"变为"74 个问题 + 攻击链验证 + 灾难分级 + 契约审查 + 可执行工程方案"——**增量不在知识量，在思考的组织方式**（能力 = 思考能力 × 思考的组织方式）。
